## 一、先想清楚三件事（动 PPT 之前）

### 1. 这次答辩的评分逻辑

课程设计答辩老师通常按这四条打分，PPT 的篇幅分配要向它们倾斜：

| 评分维度 | 大致权重 | PPT 对应章节 |
| --- | --- | --- |
| 方案设计（架构合理性、传感器选型） | ~30% | 第 3、4 章 → PPT P3~P7 |
| 实现深度（软件架构、关键算法、踩坑解决） | ~35% | 第 5 章 → PPT P8~P12 |
| 测试结果（功能演示、指标达成） | ~25% | 第 7 章 → PPT P13~P15 |
| 表达与协作 | ~10% | 全程 |

**核心原则**：老师最想看的是"你遇到了什么问题、你怎么定位、怎么解决"——这是我们这套系统最出彩的部分（6 个联调问题里有 3 个堪称教科书案例），一定要舍得花篇幅讲。

### 2. 一条贯穿全场的故事线

不要按报告章节平铺直叙，用这条故事线串：

> **"一把普通的门锁，怎么变成一个会报警、能远程管理、还防误操作的智能系统？"**
> → 三个层次递进：① 先让它能开关（感知+执行）→ ② 再让它懂安全（状态机+告警）→ ③ 最后让多设备不打架（单一真相源）。

每一部分讲完都回到这个故事线，评委会自动跟上你的思路。

### 3. 谁讲哪部分（4 人组建议分工）

| 段落 | 内容 | 讲解人 |

| P1~P3 | 开场、需求、总体架构 | 组长 |
| P4~P7 | 硬件设计 | 组员 A |
| P8~P12 | 软件设计与关键问题 | 组长 或 组员 B |

### P6 两个关键硬件设计

每个问题用"现象 → 根因 → 对策"三栏卡：

1. **ESP8266 供电**：峰值 300 mA > 板载稳压 100 mA → 独立 AMS1117 稳压板 + 大小电容并联
2. **温度采集电路**：上拉式分压 + NTC 接地侧（故障时可识别）→ 配图 4-1 重绘版
- 这页是"硬件含金量"的证明，讲的时候点名示波器抓到 3.3V→2.6V 跌落的故事（P15 还会展开）。

### P7 引脚分配（可合并进 P6）

- 两张引脚表并排放（ESP32 / STM32），如果时间紧可以只留 ESP32 一张，STM32 一句带过。
- ⚠️ 如果答辩老师偏硬件，保留此页；偏软件则合并。

### P8 ESP32 软件架构：五任务（⭐ 关键页）

- 用一张"核绑定图"：左 Core 1（taskLogic 20ms / taskSensors 100ms / taskRgb 20ms），右 Core 0（taskNetwork 500ms / taskMonitor 5s）
- 讲两点：① 为什么网络任务隔离到 Core 0（WiFi 协议栈在 Core 0，阻塞不影响键盘响应）；② 互斥锁保护共享状态。
- 图示建议：圆角矩形 + 双核底色分区，周期写在任务名下面。

### P9 三态状态机（⭐ 全场最重要的一页）

- **图 3-2 必须重绘成标准状态机图**（三个圆角状态 + 带标注的转移箭头）
- 讲三个设计要点（每个 15 秒）：
  - 多入口单出口：四条告警路径统一进 `enterEmergency()`
  - 紧急态在指令分发入口直接拦截开关门
  - 紧急态显示温度固定 50 ℃：**传感值与显示值分离**（讲清"为什么不能直接改传感器返回值"——50>45 会让告警条件恒真）
- 这页最能体现软件思维，务必讲透。

### P10 STM32 侧：按键识别与 AT 驱动

- 左半：按键状态机参数表（20ms 消抖 / 1s 长按 / 长按只报一次、报过长按不再报短按）
- 右半：AT 驱动三层封装图（发指令等关键字 → 具体指令封装 → HTTP 方法）
- 三个踩坑缩成一行图标卡：busy 重试 / 射频损坏换件 / BSSID 锁定（软 AP 的 local bit 知识点提一嘴，老师会眼前一亮）。

### P11 一个真实的性能 Bug：TCP 连接卡 5 秒

- 专用一页讲这个案例，格式：**问题代码 → 时序分析 → 修复代码**
  - 旧：`wait_for("CONNECT",5000) || wait_for("ALREADY CONNECTED",500)` —— ERROR 时必须硬等满 5s，主循环卡死 → "按键没反应"
  - 新：单循环同时匹配 CONNECT / ERROR / busy，失败立即退出并 CIPCLOSE 清场
- 用代码截图 + 红框标注差异。这是评委最容易给分的"工程素养"证据。

### P12 看板与单一真相源（⭐ 关键页）

- 上半：系统拓扑小图（三台设备 + 5 个 API 一行列出）
- 下半：讲设计缺陷→修复：
  - 缺陷：STM32 的 cmd 事件携带 mode，污染全局状态 → "退出紧急后仍无法开关门"
  - 修复：**安防模式只能由 ESP32 改写**（单一真相源）+ **有效模式折算**（`effMode(forDevice)`：同一时刻，ESP32 和 STM32 查到的"模式"含义不同）
- 用报告表 5-4 的四行折算规则做表格，高亮最后一行"主控离线 → 控制权移交"。
- 讲一句升华："这不是 bug 修补，而是把系统从'谁都能改状态'升级为'单一权威 + 视图折算'的分布式设计。"

## 四、答辩话术备忘

### 每页的开场句式

- 架构页："整个系统是一个三层结构，数据流是这样的……"
- 问题页："这里我们最初的做法是 X，实测发现了 Y 现象，定位后根因是 Z，最终改成 W。"
- 测试页："所有 20 项功能全部通过，三个关键指标实测优于设计要求。"

### 老师最可能追问的 6 个问题（提前准备答案）

1. **"为什么用两个单片机，一个不行吗？"** → 功能解耦、教学覆盖、物理分离（P4 内容）。
2. **"NTC 测温原理？为什么不用 DS18B20？"** → B 值公式 + 分压；成本与信号链教学价值（附录 B）。
3. **"紧急状态为什么温度显示 50 ℃？不怕误判吗？"** → 传感值与显示值分离，原始值仍参与告警判定（P9）。
4. **"ESP32 挂了门还能开吗？"** → 看板 15s 心跳超时后把控制权移交给 STM32；但紧急态不降级（P12）。
5. **"STM32 查询失败就拒绝开门，网络抖动会不会打不开门？"** → 是有意为之的安全取舍（保守失败），改进方向是离线密码备份认证（P17）。
6. **"密码存在哪？安全吗？"** → 目前 RAM 明文，是已知不足，改进是 Flash + 加盐哈希（诚实承认 + 给方案）。

### 时间分配（以 10 分钟为例）

开场+架构 2.5 min → 硬件 2 min → 软件 3 min → 测试+演示 2 min → 总结 0.5 min。
**宁可少讲，不要拖堂**——超时被打断的观感比少讲一页差得多。
