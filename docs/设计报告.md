## 摘　要

针对传统机械门锁难以实现远程监控、异常告警与分级权限管理的问题，本文设计并实现了一套双控制器架构的智能安防门禁系统。系统采用"感知层—控制层—管理层"三层结构：以 ESP32-S3 作为门禁主控，完成矩阵键盘密码输入、NTC 热敏温度采集、霍尔门磁状态检测、OLED 信息显示与舵机电子锁驱动，并承担布防、撤防、紧急状态的状态机管理；以 STM32F103C8T6 配合 ESP8266 模块构成独立的物理按键控制器，通过 WiFi 与网页看板交互，实现"短按开关门、长按一键报警"的现场操作能力；以 Node.js 编写的网页看板作为数据汇聚与管理中心，负责事件记录、状态可视化与远程指令下发。

系统在软硬件上分别解决了三个关键问题。硬件上，通过为 ESP8266 模块配置独立稳压电源并锁定热点 BSSID，解决了模块供电不足与同名热点误连的问题；软件上，引入互斥锁保护跨任务共享的传感器状态，解决了 FreeRTOS 多任务并发访问的数据一致性问题；系统集成上，确立了"看板为单一真相源"的权限裁决机制，解决了双控制器模式同步与紧急状态锁定的可靠性问题。

样机测试表明：温度测量误差优于 ±0.5 ℃，门磁响应时间约 20 ms，本地开门指令端到端延迟约 1.5 s，远程指令延迟约 1.0 s；密码错误拒绝、布防入侵报警、高温强制开门、紧急状态跨设备锁定与解除等设计功能均工作正常，系统连续运行稳定。本设计以较低的成本完成了从现场感知到远程管理的完整闭环，对小型场所的门禁安防改造具有一定参考价值。

**关键词**：智能门禁；ESP32-S3；STM32F103；多传感器融合；FreeRTOS；状态机；物联网

## 1 绪论

### 1.1 设计背景

门禁系统是建筑安防体系的第一道防线。传统的机械锁具依赖物理钥匙，存在钥匙易复制、丢失后无法快速注销、访问记录不可追溯等固有缺陷。随着嵌入式处理器成本下降与物联网技术普及，电子门禁已从早期的单一刷卡方式，发展为支持密码、射频卡、指纹、人脸等多种认证方式，并普遍具备联网告警与远程管理能力的综合安防终端。

在高校实验室、宿舍、办公室等小型场所，门禁改造往往面临两个现实约束：一是预算有限，难以承担商用门禁系统数千元的软硬件投入；二是现场环境差异大，既有需要在门内临时开门的实际需求，又有需要远程查看状态的运维需求。这类场景适合采用模块化、低成本的自行设计方案。

### 1.2 设计目标

本设计面向小型场所门禁场景，目标是构建一套具备以下能力的智能安防门禁系统：

1. **多方式认证开门**：支持矩阵键盘密码认证与物理按键快捷开门两种现场方式，并支持网页远程下发开门指令。
2. **多传感器环境感知**：实时采集环境温度与门体开关状态，为异常判定提供数据依据。
3. **分级安防状态管理**：支持撤防、布防、紧急三种安防状态，不同状态对应不同的告警策略与门锁权限。
4. **异常自动告警**：在布防状态下检测到非法开门，或环境温度超过阈值时，自动进入紧急状态并强制开门。
5. **跨设备状态统一**：现场按键控制器、门禁主控、网页看板三者对"当前是否处于紧急状态"的判断必须完全一致，紧急状态的解除权唯一。

### 1.3 主要工作

本设计的主要工作包括：

- 完成系统总体架构设计，划分感知层、控制层、管理层三层结构，确定双控制器分工与通信方式。
- 完成 ESP32-S3 门禁主控的外围电路设计与驱动程序开发，涵盖矩阵键盘、NTC 热敏电阻、霍尔门磁、OLED 显示屏、舵机电子锁与板载 RGB 状态灯。
- 基于 FreeRTOS 构建五任务并发架构，引入互斥锁解决多任务共享状态的数据竞争问题，并以三态状态机统一管理安防逻辑。
- 完成 STM32F103C8T6 裸机开发环境的搭建（CMake + arm-none-eabi-gcc + OpenOCD），实现按键短按/长按识别、ESP8266 AT 指令驱动与 HTTP 客户端功能。
- 设计并实现基于 Node.js 的网页看板，提供事件上报、状态查询、远程指令下发三类接口，并确立"看板为单一真相源"的跨设备权限裁决机制。
- 完成系统联调与功能测试，针对联调中暴露的供电不足、模块射频损坏、模式同步失效等问题进行定位与改进。

### 1.4 报告结构

本文共八章。第 1 章介绍背景与目标；第 2 章进行需求分析；第 3 章给出总体设计；第 4、5 章分别阐述硬件与软件设计；第 6 章讨论系统集成与通信协议；第 7 章给出测试结果与分析；第 8 章总结全文并展望改进方向。

## 3 系统总体设计

### 3.1 总体架构

系统采用三层架构，如图所示分为感知层、控制层与管理层。

**感知层**由各类传感器与交互外设构成，包括 NTC 热敏电阻（温度）、霍尔传感器（门磁）、4×4 矩阵键盘（密码与功能输入）、机械按键（快捷开关门与紧急报警）以及 OLED 显示屏与 RGB 状态灯（人机反馈）。

**控制层**由两套独立的控制器组成。ESP32-S3 作为门禁主控，承担全部的传感采集、状态判定、密码逻辑与门锁驱动，是系统的核心；STM32F103C8T6 配合 ESP8266 模块构成按键控制器，本身不具备门锁驱动能力，只负责把现场按键意图转换为网络指令。

**管理层**为运行在 PC 上的网页看板，由 Node.js 编写的轻量 HTTP 服务与前端页面构成，负责汇聚两台上报的事件、维护全局安防状态、向设备下发远程指令，并向用户提供可视化界面。

### 3.2 双控制器分工

本设计采用双控制器而非单控制器，主要基于以下考虑：

其一，**功能解耦**。门禁主控是安全关键部件，其代码应尽可能精简可靠；按键控制器面向现场操作，逻辑相对独立。两者分离后，任一方的软件更新不影响另一方。

其二，**教学覆盖**。门禁主控采用 Arduino 框架，按键控制器采用寄存器级裸机开发，同一系统内两种开发范式并存，便于对比理解。

其三，**物理分离**。按键控制器可安装于门内侧方便触达的位置，与门禁主控不必共板。

两者的职责边界如表 3-1 所示。

**表 3-1 双控制器职责划分**

| 能力 | ESP32-S3 门禁主控 | STM32F103 按键控制器 |
| --- | --- | --- |
| 传感器采集 | 温度、门磁 | 无 |
| 人机交互 | 矩阵键盘、OLED、RGB | 单按键、单 LED |
| 门锁驱动 | 有（舵机 PWM） | 无 |
| 安防状态机 | 有（撤防/布防/紧急） | 无（仅查询状态） |
| 联网方式 | 板载 WiFi | 外接 ESP8266，AT 指令 |
| 网络角色 | 上报事件、轮询指令 | 上报事件、请求权限 |
| 门锁控制权 | 常态持有 | 仅在主控离线时接管 |

需要特别说明的是最后一行。常态下门锁由 ESP32-S3 全权控制，按键控制器只是"遥控器"；但当 ESP32-S3 掉线时，看板会把门锁控制权移交给按键控制器，避免主控故障导致门体完全无法开启。这一降级策略在 6.2 节详细讨论。

### 3.3 安防状态机

系统的核心是如图 3-2 所示的三态状态机。三个状态分别为撤防（Disarmed）、布防（Armed）与紧急（Emergency）。

```
                        ┌─────────────────────────┐
         上电 / 输密码撤防 │                         │ 按 A 键 / 网页布防
        ┌──────────────►│      Disarmed 撤防       │◄──────────┐
        │                │   绿灯 · 门锁可自由控制   │           │
        │                └───────┬─────────────────┘           │
        │                        │ 门关闭才允许布防              │
        │                        ▼                              │
        │                ┌─────────────────────────┐           │
        │   输密码撤防    │       Armed 布防        │           │
        │   网页撤防      │   黄灯 · 入侵检测生效    │───────────┘
        │                └───────┬─────────────────┘   输密码 / 网页撤防
        │                        │
        │       ┌────────────────┴────────────────┐
        │       │ ① 门开超 5 s（入侵）             │
        │       │ ② 温度 > 45 ℃（高温）           │
        │       │ ③ 按键长按 1 s（人工报警）       │
        │       │ ④ 网页/按键下发 emergency        │
        │       ▼                                  │
        │  ┌─────────────────────────────────────┐ │
        └──┤         Emergency 紧急              │ │
           │  红灯 · 强制开门 · 拒绝一切开关门    │ │
           │  仅密码或网页"解除紧急"可退出        │ │
           └─────────────────────────────────────┘ │
                                                  │
                     （紧急状态不经过布防，直接回到撤防）
```

**图 3-2 安防状态机**

状态机的设计要点有三：

**第一，紧急状态的入口唯一、出口唯一。** 四条触发路径（传感器告警、人工长按、网页指令、按键控制器指令）在代码中统一收敛到同一个函数 `enterEmergency()`，保证行为完全一致——都是强制开门、红灯、OLED 跳出密码页、拒绝远程开关门。出口同样收敛到 `doDisarm()`，且必须经由密码验证或网页显式解除。这种"多入口单出口"的设计消除了状态机中行为不一致的风险。

**第二，紧急状态下拒绝一切开关门请求。** 这不是简单的界面限制，而是在指令分发的入口处直接拦截：开门与关门指令到达时若状态为紧急，指令被丢弃并提示用户。这样即使有恶意请求或误操作，也无法在紧急状态下改变门锁。

**第三，紧急状态下温度读数固定为 50 ℃。** 这一设计看似反常，实则是为了对外表达"当前处于异常事件中"。具体实现上，传感器原始值保持不变（仍用于告警判定），仅在显示与上报通道上替换为固定值，解除后自动恢复真实读数。若直接将传感器返回值改为 50 ℃，则 50 > 45 会使高温告警条件恒为真，导致告警无法退出。

选型说明：

**ESP32-S3 作为门禁主控**，主要看重其双核 240 MHz 的处理能力、内置 WiFi 与 512 KB SRAM，能够同时承担多任务调度与网络通信；板载 WS2812 RGB 灯可直接用作状态指示，省去外部指示灯。

**STM32F103C8T6 作为按键控制器**，主要出于教学目的。该芯片是高校嵌入式课程的标准平台，寄存器资源公开、资料完备，适合进行寄存器级编程练习。其 64 KB Flash 与 20 KB RAM 对于 AT 指令驱动与 HTTP 客户端而言足够。

**NTC 热敏电阻**相比数字温度传感器（如 DS18B20）成本更低，且能让学生完整实践"模拟量采集—分压计算—非线性换算—数字滤波"的信号调理链路。

**霍尔传感器**相比干簧管具有无机械触点、寿命长的优势，且多数模块已内置比较器，直接输出数字电平，便于接口。

### 4.2 ESP32-S3 门禁主控硬件设计

#### 4.2.1 引脚分配

ESP32-S3 的引脚复位状态复杂，部分引脚在启动瞬间具有 strapping 功能，若被外部电路拉至错误电平将导致启动失败。本设计在分配引脚时遵循以下原则：避开 GPIO0/3/45/46 等 strapping 引脚（GPIO0 仅作运行时输入使用）、避开 GPIO19/20（USB）、避开 GPIO26~32（Flash）、避开 GPIO33~37（PSRAM）、避开 GPIO43/44（调试串口）。

| 功能 | GPIO | 方向 | 说明 |
| --- | --- | --- | --- |
| 键盘行 R1~R4 | 12, 11, 10, 9 | 输入上拉 | 逐列扫描时读取 |
| 键盘列 C1~C4 | 8, 7, 6, 5 | 输出 | 逐列拉低扫描 |

#### 4.2.2 温度采集电路

温度采集采用上拉式分压结构：3.3 V 电源经 10 kΩ 精密电阻接至 ADC 采样节点，节点再经 NTC 热敏电阻接地，ESP32-S3 的 ADC 引脚接在节点处。

```
        3.3V
         │
        ┌┴┐
        │ │  R_series = 10 kΩ
        └┬┘
         ├─────────► GPIO1 (ADC1_CH0)
        ┌┴┐
        │ │  NTC 10K (B=3950)
        └┬┘
         │
        GND
```

**图 4-1 温度采集分压电路**

选择 NTC 接地的接法，是因为该接法下温度升高时 NTC 阻值减小、采样节点电压降低，ADC 读数变化方向与温度相反。虽然反相，但该接法在 NTC 短路时采样节点电压为 0，程序可据此识别故障；若改为 NTC 接电源侧，短路时电压为 3.3 V，与控制电路逻辑冲突。此外，NTC 接地可使采样节点在正常工作时处于中间电压区间，充分利用 ADC 的动态范围。

ADC 配置为 12 位分辨率、11 dB 衰减，输入量程约 0~3.3 V。为防止 NTC 开路或短路被误判为极端温度，程序中加入了量程保护：当 ADC 读数小于等于 0 或大于等于 4095 时直接返回 NaN，不参与后续计算与滤波。

#### 4.2.3 门磁检测电路

霍尔传感器模块采用开漏或推挽数字输出，检测到磁铁靠近时输出低电平。为避免边缘抖动造成误判，本设计未使用硬件滤波电容，而是在软件中采用"高频采样 + 连续确认"的策略：采样周期 10 ms，新状态需连续 2 次采样一致才被认可，即响应时间约 20 ms，兼顾了灵敏度与抗干扰能力。

#### 4.2.4 舵机驱动电路

舵机采用标准的 50 Hz PWM 控制，脉宽 500~2500 μs 对应 0°~180°。ESP32-S3 通过 LEDC 外设产生 PWM：LEDC 定时器配置为 50 Hz、10 位分辨率，占空比按角度线性换算后写入比较寄存器。

本设计中 0° 对应闭锁、90° 对应开锁。需要指出的是，LEDC 定时器的频率与分辨率相互制约——在 80 MHz 时钟源下，50 Hz 频率最多支持约 14 位分辨率，若设置更高分辨率将导致 `ledcSetup()` 静默失败、PWM 无输出且仅打印一行错误日志。因此本设计采用 10 位分辨率，此时占空比量化误差约为 0.2%，对应舵机角度误差小于 0.4°，对门锁应用完全足够。

#### 4.2.5 显示屏与状态灯

OLED 采用 SSD1306 驱动芯片，I²C 接口，默认地址 0x3C。由于每次刷新需传输整帧数据，占用较多 I²C 带宽，程序中采用了两级优化：一是内容未变化时不刷新，二是刷新频率限制在约 6 fps。

板载 WS2812 单总线 RGB 灯通过 RMT 外设驱动，程序中实现了淡入—保持—淡出的呼吸效果，避免固定亮色过于刺眼。三种状态用三种颜色区分：绿色表示环境正常、黄色表示门被打开、红色表示紧急状态。

#### 4.3.2 供电设计要点

这是本设计在硬件上遇到的最关键问题。ESP8266 模块在射频发射瞬间的峰值电流可达 300 mA 以上，而 STM32 最小系统板载的 AMS1117 稳压器额定输出仅约 100 mA 且无散热设计。若由 STM32 板直接为 ESP8266 供电，模块在连接热点、发送数据时会因电压跌落而复位或行为异常，表现为"AT 指令时通时不通"、"能连上网络但随即断开"等难以定位的故障。

本设计的解决方案是：为 ESP8266 单独配置一块 AMS1117-3.3 稳压模块，由 5 V 电源直接供电，与 STM32 的电源仅共地不共源。同时在模块电源引脚就近并联 100 μF 电解电容与 0.1 μF 陶瓷电容，前者应对低频大电流波动，后者抑制高频噪声。

另有两点必须注意：一是 ESP8266 为 3.3 V 器件，其 TX/RX 严禁接 5 V，否则将永久损坏；二是 CH_PD 引脚必须拉高，否则模块完全不工作。

#### 4.3.3 按键识别电路

按键一端接 PB12、另一端接地，PB12 配置为内部上拉输入，按下时读到低电平。硬件上仅用一个 100 nF 电容并联在按键两端作初步去抖，主要消抖工作由软件完成。

## 5 软件设计

### 5.1 ESP32-S3 软件架构

#### 5.1.1 任务划分

门禁主控的软件基于 FreeRTOS 构建，按职责划分为五个任务，如表 5-1 所示。

**表 5-1 FreeRTOS 任务划分**

| 任务名 | 周期 | 优先级 | 绑定核 | 职责 |
| --- | --- | --- | --- | --- |
| taskLogic | 20 ms | 4 | Core 1 | 键盘扫描、指令分发、状态机推进、显示刷新 |
| taskSensors | 100 ms | 3 | Core 1 | 温度与门磁采集，写入共享状态 |
| taskRgb | 20 ms | 1 | Core 1 | WS2812 呼吸灯效果驱动 |
| taskNetwork | 500 ms | 2 | Core 0 | WiFi 保活、指令轮询、温度定时上报 |
| taskMonitor | 5000 ms | 1 | Core 0 | 堆内存与运行状态巡检 |

任务绑定策略上，将实时性要求高的采集、逻辑、灯效任务集中在 Core 1，将网络相关任务隔离到 Core 0。这样做的原因是 ESP32 的 WiFi 协议栈运行在 Core 0，网络任务的阻塞（如 HTTP 超时）不会影响 Core 1 上的键盘响应与状态机推进。

#### 5.1.2 并发访问与数据保护

五个任务并行运行带来的直接问题是共享状态的访问冲突。以传感器状态为例，taskSensors 负责写入温度与门磁值，而 taskLogic（用于显示与告警判定）、taskNetwork（用于上报）、taskMonitor（用于巡检打印）三个任务都要读取。若不加保护，可能出现读取到一半被写入打断、导致数据撕裂的情况。

本设计的解决方案是引入 FreeRTOS 互斥量（Mutex）保护共享状态结构体。所有访问该结构体的代码路径都遵循"取锁—操作—放锁"的模式，取锁超时设为 5~10 ms，超时时降级为直接读取（32 位对齐的读写本身是原子的，可接受最终一致性）。

这里有一个值得记录的工程细节：在实现"紧急状态下温度显示固定 50 ℃"这一需求时，最初的方案是让采集函数直接返回 50 ℃。但这会导致 50 > 45 使高温告警条件恒为真，紧急状态无法退出。最终的方案是将"传感值"与"显示值"分离为两条通道——采集函数始终返回真实值供告警判定使用，另设一个显示函数在紧急态下返回固定值。这一改动看似微小，实则体现了"数据源与数据视图应当分离"的设计原则。

#### 5.1.3 键盘扫描与消抖

4×4 矩阵键盘采用"行输入上拉、列输出扫描"的方式：逐列输出低电平、其余列输出高电平，读取四行的电平状态。若某一行为低电平，则该行与该列交叉处的按键被按下。

键盘扫描的难点在于按键识别。程序维护两个状态变量：`_keyDown` 记录当前是否处于按下状态，`_lastKey` 记录上次识别到的键值。只有当检测到新键值与上次不同时，才返回一次键值。这样保证了"按住不放只触发一次"，避免功能被连续重复触发。

此外还面临键位映射与物理接线不一致的问题。调试中发现，键盘的物理接线顺序与丝印顺序恰好相反，程序中通过调整映射表的行列顺序（相当于矩阵转置加列镜像）加以适配。这一适配过程说明：矩阵键盘的映射表必须依据实际接线逐键验证，不能直接照抄器件手册。

#### 5.1.4 密码逻辑

密码模块支持四种输入上下文：上电验证、撤防验证、旧密码验证、新密码设置。程序用 `_ctx` 变量记录当前上下文，用 `_entry` 缓冲区累积输入的数字，`*` 键清空、`#` 键提交。

针对"上电后未验证密码"的场景，程序设有一个 `_pwdVerified` 标志。未验证时，功能键（A/B/C/D）一律被拦截并提示先输入密码，只有数字键、`*`、`#` 可用。这避免了未认证者通过功能键进行布防、撤防等敏感操作。

#### 5.1.5 紧急状态实现

`enterEmergency()` 函数是四条触发路径的统一入口，其执行顺序经过精心设计：

1. 设置模式为紧急；
2. 强制驱动舵机开锁（不论此前是否上锁）；
3. 清空键盘上下文，强制切换至密码输入界面；
4. 刷新 OLED 显示"!!EMERGENCY!! / enter pwd"；
5. 立即刷新 RGB 灯为红色；
6. 取消门开计时，避免叠加第二条告警；
7. 向看板上报带来源标识的紧急事件。

执行顺序的考量在于：先完成物理动作（开锁）再完成视觉反馈（显示、灯），确保用户最先感知到门已开；取消门开计时则防止在布防态下的入侵告警路径与高温告警路径重复触发。

与进入路径对应，`doDisarm()` 在从紧急态退出时还会额外执行一次上锁操作。这是因为紧急状态是以"强制开门"进入的，若不收回门锁，紧急解除后门将处于敞开状态，与"安全"的语义相悖。

#### 5.1.6 显示与指示

OLED 显示采用三行小字版式：第一行为标题（密码提示、临时消息或温度）、第二行为内容（输入的数字、消息内容或模式与门磁）、第三行为网络状态（已连接显示 IP，未连接显示 NO LINK）。为避免频繁刷新占用 I²C 带宽，程序缓存了上一帧的三行文本，内容完全相同时跳过刷新；同时限制刷新率不超过 6 fps。

RGB 状态灯采用呼吸效果而非固定亮色。实现方式是计算当前时间在颜色保持周期内的相位，据此计算亮度系数，在周期首尾各用一段淡入淡出过渡。这种实现只需一次定时器中断或周期任务调用，无需额外的硬件 PWM。

### 5.2 STM32 按键控制器软件设计

#### 5.2.1 开发环境

按键控制器采用寄存器级裸机开发，不依赖标准外设库与 CMSIS，全部外设操作通过自建的寄存器定义头文件完成。构建系统为 CMake + Ninja，编译器为 arm-none-eabi-gcc（取自 STM32CubeCLT），调试与烧录通过 OpenOCD 配合 WCH-Link 完成。

选择 CMake 而非 Keil 的原因在于：CMake 工程结构清晰、可版本控制、跨平台，且能与现代编辑器良好配合；相较之下 Keil 的工程文件为二进制格式，不利于协作与审查。

需要记录的一个工程细节是：STM32 工程中的 `.c` 源文件采用 GBK 编码（因历史原因保留了中文注释），在 UTF-8 环境下直接编辑会导致中文乱码。解决方案是在编辑器工程配置中显式声明默认编码为 GBK，新增的 UTF-8 文件单独标注。

#### 5.2.2 时钟与外设初始化

系统时钟配置为 72 MHz：外部 8 MHz 晶振经 PLL 九倍频得到 72 MHz 系统时钟，APB1 分频为 36 MHz（USART2 挂载于此），APB2 保持 72 MHz（USART1 挂载于此）。

串口方面，USART1（PA9/PA10）作为调试口，115200 波特率，用于输出运行日志；USART2（PA2/PA3）连接 ESP8266，同样 115200 波特率。USART2 采用中断接收 + 环形缓冲区的结构，避免阻塞式读取丢失数据。接收中断中加入了溢出错误（ORE）处理，防止溢出标志未清除导致中断反复触发而卡死。

#### 5.2.3 按键短按与长按识别

按键识别采用状态机实现，每 10 ms 调用一次轮询函数。

**表 5-2 按键识别参数**

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| 消抖计数 | 2 × 10 ms = 20 ms | 电平稳定 20 ms 才认可 |
| 长按阈值 | 100 × 10 ms = 1 s | 按住满 1 s 触发长按 |
| 短按判定 | 松开后判定 | 若全程未触发长按，则报短按 |

状态机的关键在于"长按只上报一次"与"长按后不再报短按"。前者通过 `longFired` 标志实现，后者通过 `wasLong` 标志在松开时判断——若本次按下期间已报过长按，则松开时不再报短按。这两个标志的组合保证了任意一次按键动作有且仅有一个结果。

#### 5.2.4 ESP8266 AT 指令驱动

ESP8266 通过 AT 指令集与 STM32 交互。驱动程序封装了几个层次：最底层是"发送指令并等待关键字"，中间层是各类具体指令的封装（连接热点、建立 TCP、发送数据），上层是 HTTP 方法封装（POST 事件、GET 查询）。

调试过程中遇到并解决了三个问题：

**问题一：模块上电后 AT 无响应。** 现象是串口能看到模块输出的 `busy p...`，但发送 `AT` 无回显。原因是模块会把上次连接的热点信息保存在 Flash 中，上电后自动重连，期间 AT 通道被占用。解决方案是将 AT 握手改为"耐心版"：在每个候选波特率下最多尝试 8 次、每次等待 1 s，期间一旦检测到 `busy` 就延时 500 ms 后重试，而非立即放弃。

**问题二：模块射频损坏。** 换用新模块前，某块 ESP8266 表现为 AT 指令能通、但 `AT+CWLAP` 扫描不到任何热点。经排查，供电正常、使能正常、波特率正常，唯独射频部分无输出，判定为模块射频或天线损坏。更换模块后立即扫描到 17 个热点，问题解决。这一案例说明：AT 指令能通并不代表模块功能完好，射频部分需单独验证。

**问题三：同名热点误连。** 现场环境中出现两个同名 SSID（电脑移动热点与他人热点同名），模块可能连接到错误的目标。解决方案是利用 `AT+CWJAP` 指令的第三个参数显式指定 BSSID，锁定目标热点。

这里还有一个值得记录的细节：电脑的 Windows 移动热点是基于 Wi-Fi Direct 实现的软 AP，其广播的 BSSID 并非网卡物理地址，而是在物理地址基础上将首字节的 local 位置 1（如 `b0:47:e9:95:0e:7f` 变为 `b2:47:e9:95:0e:7f`）。因此 BSSID 必须取自模块的扫描结果，而不能照抄网卡属性中的物理地址。

#### 5.2.5 HTTP 客户端实现

STM32 侧的 HTTP 客户端基于 ESP8266 的单连接透传模式实现，流程为：`AT+CIPSTART` 建立 TCP 连接 → `AT+CIPSEND` 声明发送长度并等待 `>` 提示符 → 发送 HTTP 报文 → 接收响应 → `AT+CIPCLOSE` 关闭连接。

在实现中发现并修复了一个影响系统响应性的隐患。原代码等待 TCP 建立结果的写法为：

```c
if (wait_for("CONNECT", 5000) || wait_for("ALREADY CONNECTED", 500)) { ... }
```

当模块返回 `ERROR` 或 `busy` 时，第一个等待既匹配不到 `CONNECT` 也识别不出错误，必须硬等满 5 秒才进入下一段判断。由于该函数在主循环中同步调用，一次失败就会导致主循环停顿 5 秒，键盘扫描完全停止，用户感受即为"按键没有反应"。

修复方案是改为单循环同时匹配多个关键字，任何失败或占用信号出现即立即退出，并在失败时主动发送一次 `AT+CIPCLOSE` 清理连接状态，避免后续 `CIPSEND` 莫名失败。

#### 5.2.6 门锁权限的判定策略

按键控制器本身不具备门锁驱动能力，它的"开关门"实为向看板发送一条指令，由看板转交给门禁主控执行。因此按键控制器必须知道自己当前是否有权发起这一操作。

设计初期采用本地锁存方案：长按触发紧急时在本地置位一个 `emergency_latched` 标志，此后短按一律失效，直到通过某种方式清除。这一方案在实际使用中暴露了两类问题：

其一，标志的清除依赖与看板的状态同步。若同步请求因故持续失败（看板接口不存在、响应过大解析失败等），标志将永远无法清除，系统表现为"永久性按键失灵"。

其二，若为同步失败增加"连续失败若干次即解锁"的兜底逻辑，则等价于"看板一挂就能绕过紧急状态开门"，破坏了紧急状态的安全语义。

最终方案改为**不做本地推断**：每次短按都实时向看板查询一次当前权限，由看板返回该设备视角下的有效模式。门禁主控在紧急态返回"拒绝"，布防态返回"拒绝"，撤防态返回"放行"，主控离线时返回"接管"。查询失败时保守地判为拒绝。这一改动使按键控制器中不存在任何"可能卡住的锁"，紧急状态何时解除完全由门禁主控决定。代价是每次按键多一次 HTTP 往返（约 100~300 ms），用户可以接受。

### 5.3 网页看板软件设计

#### 5.3.1 技术选型

看板采用 Node.js 内置的 `http` 模块实现，不引入任何第三方框架与依赖。选择这一方案的原因在于：系统规模小，接口数量有限，Express 等框架带来的便利不足以抵消部署复杂度；零依赖意味着只需安装 Node.js 即可运行，便于在任意 PC 上部署演示。

前端为单页 HTML，使用原生 JavaScript 与 CSS，通过 `fetch` 定时轮询 `/api/status` 获取最新状态。未使用前端框架的原因是页面交互简单，定时轮询足以满足需求。

#### 5.3.2 接口设计

**表 5-3 看板接口清单**

| 方法 | 路径 | 用途 | 调用方 |
| --- | --- | --- | --- |
| POST | /api/event | 上报事件 | ESP32、STM32 |
| GET | /api/status | 查询完整状态与事件列表 | 前端页面 |
| GET | /api/mode | 查询有效模式（精简） | STM32 |
| POST | /api/cmd | 网页下发指令 | 前端页面 |
| GET | /api/cmd | 设备取走待执行指令 | ESP32 |

其中 `/api/mode` 是专为 STM32 设计的精简接口。设计它的原因是 STM32 的接收缓冲区仅有 1 KB，而 `/api/status` 返回的数据包含最近 100 条事件、长度远超缓冲区，会导致解析失败。`/api/mode` 只返回一行短 JSON，字段数控制在四个以内。

#### 5.3.3 指令队列与时效控制

网页下发的指令不会直接推送给设备，而是存入一个单槽位队列，由设备轮询取走。这样设计的原因在于设备位于内网、没有公网地址，无法被动接收推送；而轮询模型的实现复杂度最低。

队列设计有几个要点：一是单槽位，新指令覆盖旧指令，避免积压；二是带时间戳，取走时校验是否超时（普通指令 10 s、紧急类指令 60 s），防止设备离线后恢复时执行过期指令造成误动作；三是一次性消费，取走后立即清空。

#### 5.3.4 状态的单一真相源

这是系统集成阶段修正的最重要的一处设计缺陷。

初版实现中，任何设备上报的事件只要带有 `mode` 字段，都会直接覆盖看板的全局状态。而 STM32 上报的指令事件中也携带了 `mode`——它的含义是"我希望系统变成这个模式"，而非"系统已经是这个模式"。于是一条 `action=arm` 的指令就会把看板的模式改为"布防"，即使 ESP32 根本没有执行；反之在紧急状态下，一条来自 STM32 的普通开关门指令也可能把"紧急"状态覆盖掉。

这一缺陷导致了实际故障：门禁主控端已通过密码解除紧急状态，但看板的状态被其他设备的事件反复改写，导致按键控制器查询到的权限始终不正确，表现为"退出紧急后仍无法开关门"。

修复方案是确立**单一真相源**原则：安防模式只能由门禁主控上报的事件改写，其他设备上报的指令事件一律不得修改模式。同时，考虑到不同设备需要的"模式"含义并不相同——按键控制器需要知道的是"我能不能动门锁"，而非"系统处于什么模式"——因此引入"有效模式"的概念，由看板根据请求方身份与各设备在线状态实时折算。

**表 5-4 有效模式的折算规则**

| 条件 | 返回给 ESP32 | 返回给 STM32 | 含义 |
| --- | --- | --- | --- |
| 主控处于紧急态 | emergency | emergency | 任何设备均不得动门锁 |
| 主控布防 | armed | armed | STM32 按键开门被拒（属闯空门） |
| 主控撤防 | disarmed | disarmed | 自由 |
| 主控离线、STM32 在线 | — | stm32 | 门锁控制权移交按键控制器 |

表 5-4 最后一行体现了重要的降级设计。门禁主控是系统核心，但若其因断电、死机或网络故障离线，门锁将完全无法开启，这对实际使用是不可接受的。因此当看板检测到主控心跳超时（15 s）时，将门锁控制权移交给按键控制器。这一降级是有边界的——若主控离线时正处于紧急状态，看板仍返回"紧急"，降级不会越过安全红线。

### 6.2 通信流程

**事件上报流程。** 设备产生事件后，以 HTTP POST 方式将 JSON 报文提交至 `/api/event`。报文包含事件类型、设备标识、温度、门磁状态、安防模式等字段。看板收到后追加时间戳与来源 IP，写入事件日志文件，同时更新内存中的状态。

**远程指令流程。** 用户在网页点击按钮后，前端调用 `POST /api/cmd` 将指令写入队列；ESP32 以 1 s 周期轮询 `GET /api/cmd`，取到指令后置入内部命令变量，由逻辑任务在下一个 20 ms 周期执行。

**按键开门流程。** 这是最复杂的一条链路，涉及三台设备：

1. STM32 检测到短按，向 `/api/mode?device=stm32` 请求权限；
2. 看板返回当前有效模式；
3. 若放行，STM32 向 `/api/event` 上报 `type=cmd, action=open`；
4. 看板校验 action 合法性，写入指令队列；
5. ESP32 轮询取到 `open`，驱动舵机开锁；
6. ESP32 上报 `door_unlocked` 事件，看板更新门锁状态。

整条链路的延迟主要来自两个轮询周期（STM32 的权限查询为即时请求，ESP32 的指令轮询周期为 1 s），实测约 1.5 s。

### 6.3 通信数据格式

**表 6-1 事件上报报文示例**

| 字段 | 类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| type | string | 事件类型 | `door_unlocked` |
| device | string | 设备标识 | `stm32` |
| temp | number | 温度（℃） | `25.8` |
| door | string | 门磁状态 | `open` / `closed` |
| mode | string | 安防模式 | `disarmed` |
| action | string | 指令动作（仅 cmd 事件） | `open` |
| src | string | 指令来源 | `stm32-key` |

**表 6-2 事件类型清单**

| 事件类型 | 来源 | 含义 |
| --- | --- | --- |
| boot | 两台 | 设备上电启动 |
| temp | ESP32 | 温度定时上报（15 s） |
| armed / disarmed | ESP32 | 布防 / 撤防 |
| door_unlocked | ESP32 | 门已开锁 |
| emergency:web | ESP32 | 网页触发紧急 |
| emergency:stm32-emergency | ESP32 | 按键长按触发紧急 |
| emergency:temp_high | ESP32 | 高温触发紧急 |
| emergency:door_open | ESP32 | 布防入侵触发紧急 |
| cmd | STM32 | 键按下发的门锁指令 |

事件类型采用"主类型 + 冒号 + 来源"的命名方式，好处是可以按主类型做前缀匹配。初版代码使用完全相等匹配，导致带来源后缀的 `emergency:web` 无法被识别为紧急状态，这是联调中修正的一处缺陷。

### 6.4 时钟与时间同步

三台设备的时钟相互独立，无法直接对齐。本设计的处理方式是：事件时间戳统一由看板在接收时打上（取服务端时间），设备本身不发送时间戳。这样所有事件在时间轴上是单调递增的，便于排序与回放。代价是无法反映网络传输延迟，但对本系统的秒级精度需求已足够。

### 7.4 问题与改进

联调阶段共暴露并解决了六个问题，汇总如表 7-3。

**表 7-3 联调问题汇总**

| 序号 | 现象 | 根因 | 解决方案 |
| --- | --- | --- | --- |
| 1 | AT 指令无响应 | 模块上电自动重连，AT 通道被占 | 握手改为耐心版，识别 busy 后延时重试 |
| 2 | 扫描不到任何热点 | 模块射频/天线损坏 | 更换模块 |
| 3 | 连接热点失败 | BSSID 抄错（软 AP 使用派生地址） | 改用扫描结果中的 BSSID |
| 4 | 按键时通时不通 | ESP8266 供电不足导致电压跌落 | 独立稳压模块 + 大小电容并联 |
| 5 | 模式与设备状态不一致 | 指令事件污染全局模式 | 确立单一真相源，引入有效模式折算 |
| 6 | 退出紧急后无法开关门 | 本地锁存标志无法清除 | 取消本地锁存，改为每次实时查询权限 |

其中问题 4、5、6 具有代表性，值得专门说明。

**问题 4** 的排查过程颇为曲折。最初的判断是软件问题，因为串口日志显示 AT 指令偶尔能通、偶尔超时。直到用示波器测量模块电源引脚，才发现在射频发射瞬间电压从 3.3 V 跌落至 2.6 V 左右，低于模块的最低工作电压。这一现象在万用表上完全看不出来（万用表测量的是平均值），必须用示波器才能捕捉。这也说明：对于间歇性故障，测量工具的选择至关重要。

**问题 5** 属于分布式系统的经典问题——多源写入导致状态不一致。初版设计把看板当作"透明的转发器"，任何设备说什么就信什么，结果三台设备各自的状态认知互相覆盖。修复的关键在于承认"不同设备对模式的语义理解不同"，并显式地为每个请求方折算其所需的视图。

**问题 6** 则属于"看似合理的兜底逻辑反而引入新风险"。为避免按键永久失灵而加的"同步失败即解锁"兜底，实质上使安全性依赖于网络的可用性。最终方案彻底取消了本地状态推断，把判定权完全交给单一权威，从而同时解决了可靠性与安全性两个问题。

## 8 结论与展望

### 8.1 结论

本文设计并实现了一套基于 ESP32-S3 与 STM32F103 双控制器架构的智能安防门禁系统。系统实现了密码认证、按键快捷操作、多传感器环境感知、三态安防状态管理、异常自动告警与网页远程管理等功能，完成了从现场感知到远程监控的完整闭环。

主要成果包括：

1. 构建了"感知层—控制层—管理层"三层架构，明确了双控制器的职责边界，并设计了主控离线时门锁控制权移交的降级机制。
2. 基于 FreeRTOS 实现了五任务并发架构，通过互斥量解决了多任务共享状态的数据竞争问题，通过任务绑定核的方式隔离了网络阻塞对实时逻辑的影响。
3. 以"多入口单出口"的方式实现三态状态机，保证四条告警路径的行为完全一致，并以指令入口拦截的方式实现紧急状态的强制约束。
4. 确立了"看板为单一真相源"的跨设备权限裁决机制，从根本上解决了多设备状态不一致问题，并使紧急状态的锁定不再依赖于任何单台设备的可靠性。

系统实测性能满足设计要求，各项功能测试全部通过，连续运行稳定。

### 8.2 不足与展望

本设计仍存在以下不足，可作为后续改进方向：

**其一，密码明文存储。** 当前密码以字符串形式保存在 RAM 中，断电即丢失，且未做任何加密处理。改进方向是将密码存入 Flash 的非易失存储区，并进行加盐哈希处理。

**其二，无访问日志审计。** 系统虽记录了事件，但未区分成功与失败的操作、未记录操作者身份（除按键来源外）。改进方向是在事件中加入认证结果字段，并在看板侧提供审计查询。

**其三，单点依赖。** 整个系统的状态维护依赖 PC 上运行的看板服务，若 PC 关机则两台设备无法协同。改进方向是将看板部署至树莓派等常开设备，或引入本地 MQTT Broker 实现设备间直连。

**其四，缺少离线自主能力。** 按键控制器在无法访问看板时拒绝一切开门操作，虽然保证了安全性，但在网络故障时降低了可用性。改进方向是在按键控制器上增加独立的密码输入能力，作为网络不可用时的备用认证手段。

**其五，舵机寿命。** SG90 为消费级舵机，长期频繁动作后存在齿轮磨损问题。改进方向是改用电磁锁或步进电机加限位开关的方案。

### 附录 B 温度换算核心算法

```c
float Thermistor::readC() {
    int adc = analogRead(_pin);
    if (adc <= 0 || adc >= (int)ADC_MAX_VAL) return NAN;  // 开路/短路保护

    float v = adc / ADC_MAX_VAL * ADC_REF_V;
    // 上拉式分压：3.3V — R_series — ADC节点 — NTC — GND
    float rNTC = NTC_SERIES_R * v / (ADC_REF_V - v);
    if (rNTC <= 0) return NAN;

    float lnR = logf(rNTC / NTC_R25);
    float invT = 1.0f / 298.15f + lnR / NTC_BETA;         // B 值简化公式
    return 1.0f / invT - 273.15f;
}
```
